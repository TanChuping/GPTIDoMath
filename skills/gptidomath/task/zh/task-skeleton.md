## 子代理

请把这件活拆给子代理并行做，每个子代理都用你能用的最强模型：判断质量一致，比换小模型省下的时间更要紧。

- 在我们这边，整个会话只算一条消息，所以每多一个并行的子代理，就多一份产出，不多花一分额度。环境允许几个就派几个（试 6 个，含下面的复核子代理）；只允许更少，就有几个用几个，并在交付里写明实际用了几个。此前实测同一时刻最多 3 个在跑，所以分波次排：一个做完再补下一个。
- 建议这样分，可按实际调整，调了说一句为什么：一个建共用索引（函数表、调用图、状态清单；`INDEX/` 已经够用就不建）；几个各负责工作清单里的一片；**一个只审不做**，把每条报上来的发现拿回去核三件事：触发路径走不走得通、能不能复现或写出最小反例、实际会不会发生；一个负责合并、去重、写回复。
- 每个子代理的指令要能独立看懂：它看不到这段对话，也看不到别的子代理。把它要用的判断标准、红线和检查表原样带上，写明它负责的范围和要交回什么。

## 中途改动

你干活期间，我们可能要加活或改某条要求。另发一条消息会打断你这一轮，所以我们改为往 `{{WORKSPACE}}/REQUEST.md` 里追加。它第一行是 `Version: N`，每追加一次 N 加一；后追加的优先于先追加的，和本文件冲突时以它为准。这个文件还不存在，就是什么都没改。

为了按时想起来看，把 `{{WORKSPACE_ROOT}}/tools/request-channel/` 里的 `channel.py`、`README.txt`、`VERSION` 拷进沙箱，先跑 `python3 channel.py --selftest`，再跑 `python3 channel.py install --sandbox-home "$HOME"`。它只在沙箱里装一个提醒：离上次检查满 15 分钟后，下一次新开的 shell 或 Python 单元会打出 `CHANNEL_CHECK_DUE`。已经在跑的 shell 或 Python 内核收不到，要照 `README.txt` 里的说明激活一下；不激活的，就在每个检查点自己调 `python3 channel.py due`。装不上就跳过，照下面的时点照样检查。

检查由你（总协调）来做，子代理不读这个文件。开工时、分活或合并之前、做重大决定之前、提醒到点时、每次阶段存档时、交终版之前，各看一次：
- 文件在 Drive 上的修改时间和上次一样，就是没有新内容。
- 时间变了，就把全文读一遍。`Version` 变大了，就照新内容办；只有时间变、版本没变，说明我们还在写，下次检查再看。
- 读到了更高的版本，或者文件和上次记下时一样没变，就记一笔：`python3 channel.py record --version N --mtime '<Drive 修改时间>'`，记了提醒会重新计时。只有时间变、版本没变，或者文件还不存在时，不要记，过一会儿再看。
- 新要求转给受影响的子代理；它们按旧版本做完的东西，合并前按新版本再核一遍。
- 每份 `NOTES.md` 里写明用到了第几版、它改了什么。

## 请我们代跑

有些检查要用到你沙箱里没有的东西：显卡、显示器、真机、联网、我们本机的平台，或者对沙箱来说太长、太大的运行。某个判断要靠这类结果时，可以请我们在本机代跑，不用另发消息。沙箱里几分钟能跑完的、读代码就能判断的，自己做。

- **怎么请：** 写 `{{WORKSPACE}}/requestfromweb.txt`，UTF-8。第一行 `Version: N`；每条请求一节，标题 `## Request N (UTC 时间)`，写清：结果用来定哪个判断、具体命令和输入、要回传哪些输出叫什么名字、怎样算成功，以及 `Blocking: yes` 或 `no`。`Version:`、`## Request` 这些标记照原样用英文写，我们的工具靠它们识别。每次整份重写，保留旧的请求；每加一条新请求版本号加一，要分几步改时最后改版本号那一行。每条请求我们都会先看一遍再跑，所以像写给同事那样写清楚。
- **怎么收：** 一般几分钟到半小时，回复在 `{{WORKSPACE}}/reply.txt`：`Version: N` 开头，每条一节 `## Reply N (Request K, 时间)`。附件就在它旁边的任务文件夹里，不在子文件夹，文件名以 `reply<N>-` 开头；`reply<N>-attachments.json` 列出各个分段、大小和 SHA-256。超过 192 MiB 的文件按原始字节分段：所有分段都下载下来，按列出的顺序拼接，再核哈希；不要把分段一个个单独解压。回复可能比附件先同步到，缺了就过一会儿再取。
- **别停下来等：** 请求发出后接着做别的。每次看 `REQUEST.md` 时顺带看 `reply.txt`，把结果转给用得上的子代理。到交付时还没回的，在 `NOTES.md` 里列出这些请求，写上命令和它们各自要定的判断。

## 你的回复到我们手里之后怎么用

- 每条发现我们都会带回完整项目核实后再动手。核得最快的，是写清位置、触发顺序和原文的条目；只有结论的，我们得从头再推一遍。
- 你看得到材料；材料之外的调用方和运行时数据你可能看不到。「这件事会不会真发生」请只写到材料能证明的程度，写明依赖的前提，可达性交给我们核。
- 修复由我们在当前代码上做，所以补丁只当参考。必须改的附一份统一 diff；大的结构调整给函数级方案就够。

## 输出格式

发现清单，按重要度排序：

```
F1  <一句话标题>
    位置：<路径:行>
    触发：<人能照着做的一串步骤>
    证据：<原文那几行，不转述>
    严重度：一定要修 / 建议修 / 知道就行
    修法：<一句话>
```

严重度按「在我们的场景下多久会真的撞上」来定：默认是一个粗心但不恶意的人在一台普通机器上，一个月内会不会撞上一次。撞不上的不算发现，在「看到但判为撞不上」下面列一行。「一定要修」超过 3 条时，回头再筛一遍。能删的防线、没人读的记录、重复的逻辑也值得报：删往往比加更值。

最后一节写「我看不到、请你们核」：因为材料边界而确认不了的事，每条写清要核什么、去哪核。这一节是给我们的活清单，不是免责声明。

## 时间与收尾

这类会话没有固定时长（跑好几个小时很常见），但可能断线，断了之后就不会再交东西。所以不限时长，只要求分阶段存档：

- 开工时在沙箱里记下时刻，自己计时，不要靠平台的定时任务或提醒。**只算真正干活的时间：** 卡住、等授权、等 Drive、工具停住的时间不算，恢复后接着算。
- **0–70 分钟：** 照清单正常干。
- **到 70 分钟：** 花约 10 分钟整理出一份完整的保底交付（结构见下），完整到「就算之后会话马上断了，我们拿它也够用」。**这不是收工**，交完接着干。
- **70 分钟之后：** 不设上限。按「至少还要干两个小时」来准备，清单没做仔细、做完整就一直干下去。和前 70 分钟唯一的区别是存档更勤：每完成一个阶段，或每隔 15–20 分钟，存一个新的带序号的阶段 ZIP 和接手说明（做到哪、下一步是什么、断了从哪接）。大件不必为了省时间拆碎或缩小。
<!-- BEGIN drive -->
- 每次阶段存档时，顺带看一眼 `REQUEST.md` 和 `reply.txt`。
<!-- END drive -->
- 出现平台要强停你的征兆（工具频繁失败、响应明显变慢、提示上下文或长度将尽）就立刻停手，交最新的阶段成品。
- 子代理守同样的节奏：在保底交付前、每次阶段存档前，把手上的东西交回来汇总。
- 交单条件是清单做仔细、做完整，不是做完几件。清单做完了，就给已有结论补证据、打磨；确实没有值得做的了再交终版。
